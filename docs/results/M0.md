# M0: setup

*Flint: GPT-2 from scratch on hand-written CUDA kernels.*

M0 built the scaffolding every later kernel relies on, and checked it end to end
with one trivial kernel on both GPUs.

## What M0 delivered

- **Build:** one CMake preset. Every build compiles for sm_75 (RTX 2080 Ti,
  Linux, GCC 13) and sm_89 (RTX 4050 Laptop, Windows, MSVC 19.44), with
  CUDA 12.4.
- **Library:** `libflint` exposes a plain C API (`include/flint/flint.h`). It
  links only the static CUDA runtime and exports only functions marked
  `FLINT_API`, on both operating systems.
- **Tests:** pytest calls the library through ctypes, with PyTorch supplying
  inputs. `scripts/sanitize.py` runs the suite under compute-sanitizer's
  memcheck, racecheck, synccheck and initcheck. Two canaries, deliberately
  broken calls, must be caught, which shows the tools really see Flint's
  kernels.
- **Benchmarks:** `flint_bench` implements the measurement protocol below and
  writes a JSON raw log per run.
- **First kernel:** `flint_copy` is a device-to-device byte copy, there to
  exercise all of the above.
- **Pre-commit check:** `scripts/precheck.sh` builds and tests each change on the
  2080 Ti before it's committed.

## Method

- **Inputs:** Flint and the baseline get identical random inputs, rotated across
  buffer sets that strictly exceed 4x the L2 cache.
- **Warm-up:** time-based, 1.5 s per size.
- **Samples:** each timed sample is at least 100 ms of back-to-back launches.
  Rounds with a shorter sample are discarded.
- **Rounds:** 10 valid rounds, each timing Flint and the baseline back to back.
  Which side goes first alternates. The tables give the median ratio and its
  range.
- **Monitoring:** an NVML thread samples clocks, clock-event reasons, power,
  memory and the process list every 10-20 ms.
  - A round is discarded if a new process appears on the GPU, or if device
    memory grows by more than 256 MiB.
  - Only thermal and hardware-slowdown reasons are flagged.
- **Copy bandwidth:** counts bytes read plus written.
  - "Rated" is 2 × max memory clock × bus width: 616 GB/s on the 2080 Ti, 192
    GB/s on the laptop.
  - "Clock-adj." uses the time-weighted mean memory clock during the samples
    instead.
- **Correctness:** after timing, Flint's output is compared bit for bit with
  `cudaMemcpyAsync`'s, with both outputs first filled with different bytes.

The tables come from the raw logs through `scripts/results_table.py`.

**What the numbers show:**
- At 16 and 256 MiB, the untuned copy is within 1.5% of `cudaMemcpyAsync` on
  both GPUs.
- On the 2080 Ti it reaches 86% of rated bandwidth. That's 88% of the bandwidth
  at the 6800 MHz its memory actually ran at under load, short of its 7000 MHz
  maximum.
- At 1 MiB a copy takes about 5 µs on the 2080 Ti, so launch overhead
  dominates.
- The laptop's 1 MiB ratios scatter, from 89% to 118%, because desktop
  applications share its GPU.

## Limitations

- **The copy isn't tuned:** 256-thread blocks, at most 4096 of them. It exists
  to test the harness, not as a target.
- **The laptop is never idle:** 15 desktop processes use its GPU, so its runs
  need `--allow-busy`. Its memory clock varies from run to run (one run averaged
  6236 MHz against its 8001 maximum), and other runs have shown thermal flags.
  Its numbers are secondary.
- **Busy detection has a gap:** a process NVML can't see, which starts during a
  size's setup (under 1 s), goes unnoticed.
- **The server's compute-sanitizer (2024.1.1 on driver 595) intermittently
  crashes** while reporting an error it caught. The canaries count that as
  caught, and diagnosis happens on the laptop.
- **No locked clocks:** the server has no root, so clocks are logged rather than
  locked. NVML may average power over about a second, so power is context only.
